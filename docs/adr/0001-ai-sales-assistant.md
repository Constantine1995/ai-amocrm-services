# ADR 0001: AI-помощник менеджера в amoCRM

- Статус: принято
- Дата: 2026-10-01

## Контекст

Тестовое задание: сервис принимает обращение клиента, сверяется с короткой базой знаний и выдаёт два блока — вежливый ответ клиенту и подсказку по допродаже для менеджера, работающего в чате amoCRM. Сдаётся видео на 1–2 минуты.

## Как устроен сервис

1. amoCRM шлёт вебхук `message[add]` на `POST /webhooks/amocrm/{secret}` (`AmoWebhookController`).
2. Сообщение сохраняется в `amo_chat_messages`; для входящего ставится задача `GenerateLeadSuggestion` с задержкой 5 секунд.
3. Задача берёт последние 20 сообщений сделки, отправляет их в `SalesAssistant` (Ollama, `qwen2.5:7b`) вместе с базой знаний.
4. Ответ модели (`SalesSuggestion`) уходит примечанием в сделку через `AmoCrmClient` и сохраняется в `amo_suggestions`.

Для проверки без amoCRM есть команда `php artisan amo:suggest "текст клиента" "M: текст менеджера"`.

## Решения

### База знаний целиком в промпте, без RAG
`resources/prompts/knowledge_base.md` (около 60 строк) вставляется в системный промпт при каждом запросе. Модель не дообучается. При таком объёме это проще и точнее поиска по эмбеддингам. RAG — следующий шаг при росте базы.

### Ответ модели — черновик для менеджера, а не сообщение клиенту
Подсказка пишется примечанием в сделку, менеджер сам решает, что отправить. Это же основная защита от подмены инструкций в тексте клиента: в промпте диалог помечен как данные (теги `<dialog>` и прямая инструкция), но модель на 7B может этого не соблюсти.

### Вывод модели ограничен JSON-схемой
Схема передаётся в параметр `format` Ollama. Если модель уходит в иероглифы (бывает у Qwen), делается один повторный запрос, затем исключение.

### Две таблицы в одной миграции
`database/migrations/2026_10_01_000000_create_amo_chat_tables.php` создаёт:

- `amo_chat_messages` — сообщения клиента и менеджера;
- `amo_suggestions` — ответы модели: все поля подсказки, имя модели, флаг `note_sent`, ссылка на последнее сообщение клиента (`amo_chat_message_id`, уникальный ключ).

Таблицы раздельные, потому что одна подсказка отвечает на несколько сообщений, а у сообщений менеджера ответа нет. Сообщения передаются модели как история диалога; подсказки в промпт не попадают, это журнал для контроля качества и защита от дублей.

### Подсказка сохраняется после отправки примечания
Если amoCRM вернул ошибку, запись не создаётся и повторная попытка проходит целиком. Если сделка удалена (код ошибки 226), подсказка сохраняется с `note_sent = false`, задача не падает.

### Одна подсказка на пачку сообщений
Три механизма в `GenerateLeadSuggestion`:

1. Уникальная задача на сделку (`ShouldBeUniqueUntilProcessing`) с задержкой 5 секунд — сообщения, пришедшие до старта, попадают в одну генерацию.
2. После генерации задача проверяет, не появилось ли в сделке более новое сообщение. Если появилось, устаревшая подсказка не отправляется и не сохраняется: новое сообщение уже поставило свою задачу. Цена — подсказка приходит позже.
3. Если на последнее сообщение клиента подсказка уже есть, задача выходит без вызова модели. Это закрывает дубль при повторной доставке вебхука.

### Ответ менеджера определяется через API событий, а не через вебхук
Проверка на живом аккаунте (2026-10-01) показала: вебхук `message[add]` приходит только для входящих сообщений. На ответ менеджера amoCRM шлёт лишь `talk[update]`, без текста. Поэтому строк `direction = outgoing` в `amo_chat_messages` на практике не бывает.

Факт ответа берётся из `GET /api/v4/events` с фильтром `outgoing_chat_message` и временем от последнего сообщения клиента (`AmoCrmClient::hasManagerRepliedSince`). Задача спрашивает дважды: до генерации и после неё, перед отправкой примечания. Если менеджер ответил, подсказка не создаётся.

- Фильтр событий по сделке чат-события не возвращает, поэтому сделка сверяется в коде.
- События с `created_by = 0` (автоответы) ответом менеджера не считаются.
- Если API событий недоступен, подсказка всё равно создаётся: лишняя подсказка дешевле пропущенной.
- В событии нет текста сообщения. Модель не видит реплик менеджера, история диалога для неё состоит только из сообщений клиента. Получить текст стандартным API не удалось: Telegram подключён встроенной интеграцией amoCRM.

### Вебхук отвечает сразу, генерация в очереди
amoCRM ждёт быстрый 2xx. Очередь — `database`, 3 попытки, паузы 10 и 30 секунд. Секрет сравнивается через `hash_equals`, при несовпадении 404.

## Что не проверено и известные ограничения

- Модель не видит текст ответов менеджера (см. выше), поэтому рекомендация «по работе менеджера» строится только по сообщениям клиента.
- Локальная модель на 7B нарушает правила промпта: на живом сообщении выдумала дозировку, в прогоне — трек-номер заказа. Проверки ответа кодом (цены, дозировки) нет.
- `retry_after` очереди (90 с) меньше таймаута задачи (240 с). При одном воркере это безопасно; при нескольких медленная генерация может запуститься дважды.
- Флаг «ответа нет в базе знаний» — самооценка модели, она может ошибаться.
- Проект требует PHP 8.3+. Системный `php` на машине разработки — 8.2, тесты запускать так: `/opt/homebrew/Cellar/php/8.4.7/bin/php artisan test`.
- Laravel Boost установлен, но MCP-сервер в проекте не настроен (нет `.mcp.json`).

## Тесты

19 тестов: вебхук (сохранение, исходящее сообщение, повторная доставка, неверный секрет, сообщение без сделки), задача генерации (примечание, удалённая сделка, ответ менеджера в базе, ответ менеджера по событиям amoCRM, чужие сделки и автоответы, недоступный API событий, сохранение подсказки, повторная задача, ошибка amoCRM, сообщение во время генерации), `SalesAssistant` (схема, экранирование текста клиента), `SalesSuggestion` (текст примечания).

В `GenerateLeadSuggestionTest` каждый тест задаёт ответ amoCRM через `fakeAmoCrm()`: в `Http::fake` побеждает заглушка, зарегистрированная первой, поэтому общую заглушку в `setUp` держать нельзя.

## Расхождения с видео

На видео сказано неточно:

- «В SQLite сохраняются вопросы и ответы, и это используется моделью» — на момент записи сохранялись только вопросы. Сейчас сохраняются и ответы модели, но в модель передаётся только переписка.
- «Модель обучена на промптовых данных» — модель не обучалась, база знаний передаётся в промпте.
- «14 тестов» — два из них были заглушками Laravel (удалены), а тест удалённой сделки ничего не проверял (исправлен).
